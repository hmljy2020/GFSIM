# 普通与 Heavy Mesh：工作负载和并行性能报告

这个基准保持现有 8×5 Mesh、40 个节点、214 条队列和全部流量不变。
每个节点每拍额外求值一条 fake ALU 指令，其宿主机计算量由迭代次数控制。
这样可以单独观察 Work 粒度对并行收益的影响，而不混入拓扑、流量或模拟
周期数变化。

这里的“重指令”是宿主 CPU 上真实执行的整数依赖链，不是 sleep、忙等时间
或增加 SimQueue 延迟。仅增加模拟延迟通常不会增加每次 Work 的计算量。
本实验不声称建模某种真实指令的多拍延迟或流水线占用。

## Mesh 在模拟什么

可以把这个 Mesh 理解为 **40 个转发站组成的方格路网**：横向 8 个、纵向
5 个，每个站只直接连接上、下、左、右的相邻站，边界不绕回另一侧。
一个 MeshNode 就是一个转发站；它负责收包、选择下一站、排队和转发。
物理连接不是任意两站直连，远处的站之间要经过多个中间站。

例如，节点 0 在左上角，节点 10 在第 2 行第 3 列。0 发给 10 的包走
`0 → 1 → 2 → 10`：先横向到达目的列，再纵向到达目的行，这就是 XY 路由。
到站后进入本地交付队列，由测试台取走并检查。

每个方向的 queue 可以理解为只能放 **2 个包的小候车区**，传入的包下一拍
才对接收方可见。相邻站之间的两个方向各有一条队列。整个网络有 134 条
有向站间队列，加上每站一条注入队列、一条交付队列，共 214 条。

每一拍，测试台先尝试发包，各节点处理已经可见的包，测试台再验收已经
到达交付队列的包。拍末统一推进队列和提交状态；新写入的包下一拍才能
继续前进。因此，即使程序按顺序调用节点，也不能让一个包在同一拍穿过
很多站。“拍”是模型时间，报告中的毫秒是电脑实际运行仿真花的时间。

## 普通 Mesh 注入了什么 workload

这里注入的是一轮固定的 **所有节点互相发包** 的通信任务：每个节点给其余
39 个节点各发 1 个包，总计 `40 × 39 = 1560` 包，不给自己发包。
节点 0 依次发给 1、2、…、39；节点 1 依次发给 2、3、…、39、0，其他节点
按同样规律轮转。目的地址顺序固定，重复运行会得到相同的包时序。

40 个源从第 1 拍同时开始发包；只要还有待发包且本地注入队列有空间，
每个源每拍就尝试发 1 个。因此全网发包上限是 **40 包/拍**。队列满了就
等下一拍重试，不丢包、不跳过目的地。每个目的地每拍最多验收 1 个包。
每个源成功发完 39 个就停止注入，网络继续运行到所有包收完。

这些包只携带编号、源节点、目的节点和累计跳数四个整数字段。当前 workload
没有程序指令流、矩阵计算或大块业务数据；包按共享指针逐站交接，不反复
复制大载荷。包也没有进一步拆成 flit，所以不能把这里的“包/拍”直接解释
为某个真实硬件的字节带宽。

节点每次 Work 做的事情很短：查看最多 5 个输入队首（本地和四个方向），
算出每个包下一步该往哪走，再给各输出选择一个输入。如果几个包争抢同一
出口，就轮流给机会；出口队列满了，包原样留在输入队列里等待。每个输出
每拍最多发送 1 个包，不同输出可以同时发送，所以一个节点一拍不一定只
转发 1 个包。这里有通信竞争和排队，但单次决策只涉及少量判断与队列操作。

### 流量强度如何理解

这是每源尽可能持续注入的有限批次流量，存在出口争用和队列反压；它不是
无限持续灌流的饱和吞吐测试。全程统计包含开始填充网络、源陆续发完、以及
最后排空网络的阶段，不能用平均值断言所有链路都已经饱和。

| 指标 | 数值与含义 |
| --- | --- |
| 发包总量 | 1560 包，每个源 39 包 |
| 尝试注入速率上限 | 每源 1 包/拍，全网最多 40 包/拍；实际受队列空间限制 |
| 整轮完成时间 | 132 拍 |
| 整轮平均交付率 | `1560 / 132 ≈ 11.82` 包/拍，全网合计，包含启动与排空 |
| 节点间转发总量 | 6760 跳，平均每包约 4.33 跳，不含本地注入/交付 |
| 平均包延迟 | `19246 / 1560 ≈ 12.34` 拍，从成功注入到验收 |
| 模块求值次数 | `40 × 132 = 5280` 次节点 Work，空闲节点也每拍调用 |
| 队列推进次数 | `214 × 132 = 28248` 次，空队列也每拍推进 |

所以，“网络里有很多包在排队”和“仿真程序每次 Work 很费 CPU”是两个
不同的维度。普通 Mesh 有完整的路由、争用和反压行为，但包很小、节点
逻辑很短；把这类小任务分给线程后，同步和调度开销就容易占较大比例。

## Heavy Mesh 加重了什么

heavy 版本保留上述 1560 包和全部网络行为，只额外让 **每个节点每拍做一段
整数计算**。可以理解为每个转发站除了寄包，还要完成一份指定长度的算术
作业。这份作业与收到几个包无关：没有包、出口堵住时也照做，每个节点
的计算量一样。这能单独测试“每次 Work 变重后，线程并行是否更划算”。

| 每节点每拍迭代轮数 | 一次完整仿真的额外 ALU 轮数 |
| ---: | ---: |
| 0（普通 Mesh）| 0 |
| 1,000 | 5,280,000 |
| 10,000 | 52,800,000 |
| 100,000 | 528,000,000 |

每轮包含多次移位、异或和一次乘法，下一轮依赖上一轮结果。这里的
100,000 轮既不表示 100,000 个包，也不表示模拟指令占用 100,000 拍。
它让宿主 CPU 真正多做计算，但整个网络仍在第 132 拍完成。

### 实现与校验

MeshBench 构造函数新增第三个可选参数 `fakeIterations`，默认 0，保持普通
Mesh 行为。该值在构造时传给所有 MeshNode，不在运行期间修改。

每个节点每拍执行一次 FakeAlu：对私有 64 位状态重复右移/异或、左移/异或、
右移/异或、乘常数的依赖链。无符号整数溢出按模 2^64 定义，结果写入待提交
状态，并在 Xfer 提交。下一拍继续使用上拍结果；Reset 恢复由节点 ID 决定的
固定种子。迭代次数为 0 时跳过这段计算。

最终状态通过 FakeChecksum 暴露并由基准验证、写入 CSV，避免计算被优化
消除。FakeRounds 记录实际执行的迭代轮数，必须等于
`fakeIterations × 40 × 132`。一轮是多条宿主整数操作，不等同于一条机器指令。

fake ALU 不访问队列、不修改 Packet、不增加模拟周期，也不标记网络进展。
真实注入、路由、交付才调用 MarkProgress，因此额外计算不会掩盖网络死锁。
所有配置仍需得到 1560 包、132 拍、6760 跳、总延迟 19246 包·拍。

## 构建与运行

```sh
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build build-release --target mesh_heavy_benchmark
./build-release/mesh_heavy_benchmark \
  --iterations 0,1000,10000,100000 --workers 0,1,2,4,8 \
  --batches 7 --repeats 2 --warmup 1 --output heavy-mesh.csv
python3 examples/mesh/summarize_heavy.py heavy-mesh.csv
```

`workers=0` 表示不配置并行切分的串行基线；`workers=1` 也会经过执行器。
工作线程数不包含主线程。默认迭代数和线程数与上例一致；数值越大，运行
时间越长。`--help` 显示全部选项。Linux 上可使用 taskset 将整组线程限制
在同一 NUMA 节点内的一组 CPU，至少为工作线程和主线程留足 CPU；这不会
为单个工作线程逐一固定 CPU。

每个负载/线程配置只 Build 一次，预热后复用工作线程。计时范围仅为 Run，
排除 Build、Reset、销毁、结果校验和 CSV 输出。日志关闭且不启用 trace。
每批轮换配置执行顺序，减少顺序偏差；每次运行校验逐包注入/交付时序、
网络统计、fake 轮数和同一负载下跨线程数一致的校验和。

CSV 保留每次运行的墙钟时间、进程总 CPU 时间、校验和和网络统计。
汇总脚本先计算每批的均值，再给出这些均值的中位数、最小值、最大值、
相对串行加速比和工作线程并行效率。性能结果是手动实验，不设置不稳定的
CI 加速比阈值。注意区分墙钟加速与总 CPU 消耗。

## 验证

heavy_mesh 在 0、17、257 轮下逐拍比较串行、1/2/4 工作线程与普通 Mesh 的
队列快照及逐包时序，验证 fake 状态跨线程一致和 Reset 重跑一致。
另有停住全部注入队列的测试，确认 fake 计算不会阻止无进展死锁检测。
heavy_mesh_benchmark 和 heavy_mesh_summary 验证可执行基准、CSV 和汇总流程。

## 之前普通 Mesh 的测量结果（2026-11-27）

之前比较的是同一份普通网络流量在两种执行安排下的性能。第一版把节点
分给工作线程，但仍由主线程推进全部 214 条队列；修改后，队列推进也随
关联节点分配给工作线程。两者都是 1560 包、132 拍，没有额外 fake ALU。

| 执行安排 | 串行耗时 | 1 工作线程 | 2 工作线程 | 4 工作线程 |
| --- | ---: | ---: | ---: | ---: |
| 队列由主线程推进（旧版复测）| 60.400 ms | 63.705 ms（0.95×）| 51.941 ms（1.16×）| 46.859 ms（1.29×）|
| 队列随节点分配到工作线程 | 60.540 ms | 66.767 ms（0.91×）| 40.785 ms（1.48×）| 28.645 ms（2.11×）|

括号为相对各行串行基线的加速比。4 线程耗时从 46.859 ms 降到 28.645 ms，
减少约 39%；说明把队列推进留在主线程确实限制了此前的收益。但这一步之后
仍然只有约 2.11 倍加速，因此又进行了下面的 heavy 计算粒度实验。

这组旧实验同样使用 Kunpeng-920、GCC 10.3.1、C++11 Release，日志与 trace
关闭，框架断言实现不变；进程限制在同一 NUMA 节点的 CPU 0–7。
每配置测 9 批，每批重新 Build、预热 2 次，再计时 10 次；取 9 个批均值的
中位数。Run 计时排除 Build、Reset、销毁和运行后的校验。
保留了[主线程推进队列的原始数据](results/kunpeng920-ordinary-main-queues.csv)和
[工作线程推进队列的原始数据](results/kunpeng920-ordinary-worker-queues.csv)。
旧 CSV 的 `phase=run` 行是仿真运行耗时，`build`、`destroy` 行不计入表中。

## 普通与 Heavy Mesh 的统一扫描结果（2026-11-27）

机器为 Kunpeng-920 / aarch64，GCC 10.3.1，C++11 Release（`-O3 -DNDEBUG`，
框架 GFSIM_ASSERT 仍启用且实现未修改）。进程通过 `taskset -c 0-15` 限制在
NUMA 节点 0 内，工作线程和主线程可在这些 CPU 上调度。使用上面的默认
扫描参数：每配置预热 1 次，7 批，每批 2 次。表中为批均值的中位数，
括号内为同一负载相对串行的加速比。

下面全部采用队列随节点分配到工作线程的实现。0 轮这一行就是普通 Mesh
在本次扫描中的对照结果。它与上面的旧实验使用不同的 CPU 范围和批次配置，
因此分别保留；分析 heavy 的加速比时，使用本次扫描中各负载自己的串行基线。

| 每节点每拍 ALU 轮数 | 串行耗时 | 2 工作线程 | 4 工作线程 | 8 工作线程 |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 60.880 ms | 41.211 ms（1.48×）| 29.318 ms（2.08×）| 25.279 ms（2.41×）|
| 1,000 | 80.896 ms | 52.628 ms（1.54×）| 34.805 ms（2.32×）| 27.339 ms（2.96×）|
| 10,000 | 264.590 ms | 144.824 ms（1.83×）| 80.479 ms（3.29×）| 50.528 ms（5.24×）|
| 100,000 | 2094.978 ms | 1057.841 ms（1.98×）| 538.241 ms（3.89×）| 279.485 ms（7.50×）|

1 工作线程在普通负载下为 65.721 ms，相对串行慢约 8%；最高负载下为
2099.668 ms，相对串行仅慢约 0.2%。最高负载的 8 线程批均值范围是
278.823–280.437 ms，4/8 线程并行效率分别约 97.3%/93.7%。

40 个节点保持不变时就能接近 8 线程线性加速，说明这个规模足以提供本次
测试所需的并行任务。普通 Mesh 的 Work 计算较轻，主线程工作、任务调度、
阶段同步和共享服务等开销占比更高；加重独立计算后这些开销被摊薄。
本实验支持计算粒度是限制原示例收益的重要因素，但没有分别测量各项开销，
也没有证明拓扑规模完全不影响扩展性。

fake ALU 是均匀、私有状态上的计算密集负载，且每拍包括节点空闲时也会
计算；结果不能直接外推到访存密集、节点负载不均或真实指令执行模型。
仅增大模拟指令延迟而不增加宿主运算量，也不能复现这里的加速趋势。

全部 280 次计时运行均通过网络时序、校验和与轮数验证。保留了
[逐次原始数据](results/kunpeng920-heavy-mesh.csv)和
[完整汇总（含 1 线程、批均值范围与效率）](results/kunpeng920-heavy-mesh-summary.csv)。
